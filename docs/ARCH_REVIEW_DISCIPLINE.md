# 架构审查纪律（不可推翻，只追加）

> STATUS: ACTIVE — 2026-11-14 操作者定调。出处：[#1200](https://github.com/ceer-quant/BlitzkriegBot/issues/1200)（v0.4.3 总计划）。配套裁决与 PR 序列见该单；#1199（v0.4.2 StoreApi）为第一块范本。

## 架构终态

六个 API 层 + 可插拔后端，业务代码零直连：

| API 层 | 职责 |
|---|---|
| StoreApi | 配置/状态持久化（env 过渡 → SQLite 目标 → 任意 DB） |
| MarketDataApi | 行情数据（回放 / dry 模拟 / 真实交易所） |
| ExecutionApi | 下单/撤单/成交回报（paper / dry / 真实） |
| StrategyApi | 策略注册与生命周期（cdylib / Lua / 内置） |
| RiskApi | 账户级风控与出场纪律 |
| EventApi | 事件/审计/通知 |

配套裁决（2026-11-14）：架构阵痛期结束——不修补旧配置文件，全面迁 SQLite；任何数据口径、任何状态统一到 API 层；PR 只接受增利润/优化性能/扩展生态，擦文件屁股的一律拒绝合并。

## 审查判据（任一命中即拒）

**0.4.3 起所有 PR 以全局架构师视角审判，拒绝一切耦合：**

1. **依赖方向**：只能上层依赖 API 层；API 层禁止反向 import 业务/venue/存储细节；循环依赖 = 拒
2. **实现泄漏**：业务代码出现 env 键名 / SQL 表名 / venue 专有概念 / 文件路径 = 拒（不管 CI 门禁是否已覆盖该层）
3. **同域散落**：改一个域需要动 3+ 个不相邻目录 = 拒，先按域归位再提功能
4. **中间态**：一半走 API 一半直连 = 拒；迁移必须整域收口，不许半途合并
5. **接口省略**：为省事把别人的内部结构透传出去（而非经 API 类型转换）= 拒

## 审判问题（唯一）

> **这个 PR 让系统更接近「六个 API 层、可插拔后端」的终态，还是在加深耦合？**

后者无论功能多急都不合。
