## 10. 内存门禁（#206 落地，2026-09-21）

§1–§9 是**测量与归档**；本节是**判定标准**。此前 `docs/perf/*.json` 里的数字没有任何读者：内存涨了不会让任何东西失败（`soak-monitor.mjs` 只记录 `coreRssMb`，两条 soak 门禁只查存活与进度，CI 无性能 job），因此「内存从基线到目标」只是一个快照，不是验收条件。

### 10.1 阈值（什么算失败）

`node scripts/e14-memory-baseline.mjs` 现在**判定**，退出码语义：`0` 在预算内 · `1` 超预算 · `2` 测量跑不起来。

| 规则 | 参数 | 失败条件 |
| --- | --- | --- |
| 绝对上限 | `--max-peak-rss-mb N` | 峰值 RSS > N MB（打印峰值、终值、超出量） |
| 相对基线 | `--baseline F --max-ratio R`（R 默认 **1.15**，即 E14「−15%」目标读作增长预算） | 峰值 RSS > R × 基线峰值 |
| 未采到样本 | （有 `--max-peak-rss-mb` 时恒生效） | 峰值 = 0（进程没起来/没应答）→ **不算通过**，预算「未被证明」 |

- 两条规则**默认都关**：不带参数就是纯测量（`--seconds 30` 归档 + 打印），门禁是显式开启的，探索性复测不会被一个它没声明的预算拒掉。
- **跨平台比例不可比**：`ps` 的 RSS 是内核对两种分配器（macOS libmalloc vs glibc）的记账。基线文件记录 `platform`；平台不同则比例规则**不适用并大声说明**（只保留绝对上限），基线缺 `platform`（v0.2 之前的归档都是）则按本次运行平台假定并同样说明——「静默跳过」和「通过」在输出上无法区分，这是门禁变绿数周的经典方式。
- 归档默认写 `target/perf/e14-mem-run.json`（gitignore）。往**被 git 跟踪**的 `--out` 写会直接失败，除非显式 `--allow-tracked-out`——归档基线是人肉维护的，这条与 §10.3 是同一个缺陷的两半。
- `--self-test` 用**手工算好的 fixture** 跑同一个 `verdict()`，其中包含**必须失败**的样例（超上限、1.20× 基线、没采到样本）；「不会失败的门禁不携带信号」。

### 10.2 怎么跑

```bash
# 本地完整复测（30s 采样，只测量不判定）
node scripts/e14-memory-baseline.mjs --seconds 30

# 本地按 §4 归档基线判定（同平台才有意义；本机 macOS）
node scripts/e14-memory-baseline.mjs --seconds 30 --max-peak-rss-mb 96 \
  --baseline docs/perf/e14-mem-baseline.json --max-ratio 1.15

# 纯逻辑自检（毫秒级，不需要构建）
node scripts/e14-memory-baseline.mjs --self-test
```

CI（`.github/workflows/ci.yml` 的 `rust-check` job，紧跟 `Test` 之后，复用该 job 已构建的 release 二进制）：

1. `--self-test`——纯逻辑，秒级；
2. run 1：`--seconds 15 --out target/perf/e14-mem-ci-run1.json`（只测量，为 run 2 提供**同 runner 同平台**的基线）；
3. run 2：`--seconds 15 --max-peak-rss-mb 96 --baseline target/perf/e14-mem-ci-run1.json --max-ratio 1.15`。

本机实测：15s 档单次 ≈ **15.5s** 墙钟（3s 档 ≈ 3.5s），峰值 16.2–16.4 MB。CI 上跑两档 ≈ 31s + 一次 `ps` 采样开销，故**没有**另开 job（另开 job 会再付一次 release 构建，数分钟），也没有降级为 daily——**未在 GitHub runner 上实测过耗时**，若该 job 变慢，把它挪成 `schedule` 触发的独立 job 即可，脚本本身不用改。

> 诚实的口径说明（承接 §8）：RSS 在 macOS 上受 libmalloc 页级高水位影响，**不是**本项最灵敏的口径（dhat 分配量才是）。因此 CI 的绝对上限刻意宽松（96 MB，约为归档峰值的 5×——拦的是数量级级别的泄漏，不是 5% 的抖动），而 run1↔run2 的比例只回答「同一个二进制跑两遍有没有意外增长」；**紧的跨平台比例不存在**。基线文件现在记录 `platform`，将来在 Linux 上归档一次基线，就能让 CI 用 `--baseline` 做紧比较——列为跟进项。

### 10.3 超阈值时怎么办

1. **先复跑一次**排除噪声（RSS 采样粒度 1 KB、采样间隔 250 ms；两次都超才算）。
2. 读输出里打印的**峰值、终值、基线峰值**，以及 `target/perf/*.json` 的 `samples[]`：终值≈峰值且曲线平 → 水位高但无泄漏；曲线持续爬升 → 泄漏。
3. 定位到分配点（**主口径**）：`cargo test -p blitzkrieg-core --release --test dhat_profile -- --nocapture`，摘要打在日志里，明细在 `target/dhat/dhat-heap.json`（看 `pps[].tb` 排序的 top 站点）。
4. **只有人可以把预算调高**：改预算＝改 `docs/perf/e14-mem-baseline.json`（新归档一份，保留旧文件）**和** `ci.yml` 里的 `--max-peak-rss-mb`，同一个 PR、commit message 写明理由（「为什么这次增长是预期的」）。禁止静默抬高阈值——那正是 §10 开头那个「数字没有读者」的缺陷换个形式复发。

### 10.4 dhat 归档的位置与「人类维护」边界（#206）

- `tests/dhat_profile.rs` 现在把 profile 写到 **`target/dhat/dhat-heap.json`**（按 `current_exe()` 推导，跟随实际的 target 目录/`CARGO_TARGET_DIR`/CI 缓存，永远落在 gitignore 内），并在 stdout 打印一行摘要：总分配字节/块数 + 退出时存活字节/块数。测试只断言「profile 非空」（profiler 悄悄不写了必须红），**不**断言字节阈值：dhat 总量是工具链+profile+目标平台的函数，阈值会变成伪装成不变量的平台特定数字。
